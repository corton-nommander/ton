# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The repo has **three toolchains**:
- **TypeScript / Blueprint** (root `contracts/`, `wrappers/`, `tests/`, `scripts/`) — the original FunC/Tolk contracts (legacy FunC `WalletSpam`, `StaticTps`, FunC jetton), their wrappers/tests, and the original TG bot. Mostly legacy now, **except `StaticTps`**, which the Go bot still drives (`/start`, `/shards`).
- **Acton / Tolk** (`jetton-prepaid/`) — the **current** on-chain contracts, all Tolk: a plain **prepaid** jetton (`JettonMinter`/`JettonWallet`) and the **rewritten Tolk `WalletSpam`** self-replicating pool, plus Acton deploy/test scripts. Compiled with the `acton` CLI.
- **Go** (`go-spam/`) — the production load generator + actively-maintained TG bot. Targets the **Acton/Tolk** contracts (embeds their compiled code blobs).

The WalletSpam pool keypair is a raw 32-byte ed25519 seed in `jetton-prepaid/pool.key` (auto-generated + saved on the first deploy, gitignored). The Acton deploy and the Go bot both read that file — `crypto.seedToKeyPair` == `ed25519.NewKeyFromSeed` — so pool addresses match. (The V5R1 control wallet still uses a 24-word mnemonic via `WALLET_MNEMONIC`; the legacy TS scripts still use `mnemonic.txt`.)

**Docs live in `docs/`** (only `README.md`, `CLAUDE.md` and `AGENTS.md` stay at the repo root):
`docs/LOADTEST_RUNBOOK.md` (how to prepare/run/record a load test + the Stress-tests sheet),
`docs/NETWORK_HEALTH_CHECKS.md` (analysing a run), `docs/DEVNET_INTEGRATION.md`, `docs/JETTON.md`.
The load-test helper is `scripts/netcheck.py` (`config`/`diff`/`status`/`run`).

## Build & Test Commands

### TypeScript
```bash
yarn build                          # Compile all contracts (blueprint build)
npx blueprint build <ContractName>  # Compile a single contract
yarn test                           # Run all tests (jest --verbose)
npx jest tests/StaticTps.spec.ts    # Run a single test file
yarn typecheck                      # Type-check without emitting (tsc --noEmit)
yarn format                         # Format with Prettier
yarn format:check                   # Check formatting
```

### Acton / Tolk (`jetton-prepaid/`)
```bash
cd jetton-prepaid
acton build                          # compile all contracts -> build/<Name>.json (base64 code_boc64 + hash)
acton build WalletSpam               # compile one contract
acton test                           # run all Tolk sandbox tests (tests/*.test.tolk)
acton test tests/WalletSpam.test.tolk
acton check                          # type-check all sources incl. scripts
acton wrapper <Name> [--test]        # (re)generate wrappers/<Name>.gen.tolk (+ test stub)
acton fmt                            # format Tolk sources
```
Requires the `acton` CLI on PATH: `export PATH="$HOME/.acton/bin:$PATH"`. **Regenerate the wrapper after changing a contract's message structs**, or the generated `send*` helpers go stale.

### Go (`go-spam/`)
```bash
make                  # from the REPO ROOT: build all binaries -> go-spam/build/{bot,spam,deploy,tpsmeter}
                      # (make bot | make spam | make deploy | make tpsmeter | make vet | make test | make clean)
cd go-spam
go build ./...        # build everything (cmd/bot, cmd/spam)
go vet ./...          # static checks
go test ./...         # run unit tests (incl. cross-toolchain address parity)
```
The root `Makefile` is the one-command build for deploys: `git pull && make`, then run `./go-spam/build/bot`.

## Running Scripts

Blueprint scripts (require network): `yarn blueprint run <scriptName>`

Env vars are used instead of CLI args (blueprint eats `--` flags):
```bash
COUNT=1000 FREQ=10 yarn blueprint run jettonSpam
```

Standalone TS scripts: `npx ts-node scripts/tpsCli.ts ...`

**Acton/Tolk deploy** (`jetton-prepaid/`) — stands up the minter + the whole WalletSpam pool `[0, count]` from ONE signed external. Env-driven (non-interactive):
```bash
cd jetton-prepaid
acton script scripts/deploy.tolk                       # emulate
acton script scripts/deploy.tolk --net testnet         # broadcast
# env: JETTON_DEPLOYER, JETTON_ADMIN_ADDRESS, JETTON_URI, WALLETSPAM_COUNT,
#      WALLET_VALUE, JETTON_VALUE, DEPLOY_CHUNK, DEPLOY_JETTON  (single funding lever)
```

**Original TS Telegram bot** (legacy, still functional):
`TELEGRAM_BOT_TOKEN=... WALLET_MNEMONIC=... yarn bot:tps`

**Go Telegram bot** (the one actively maintained). Runs from the repo root or `go-spam/` — `POOL_KEY_FILE` auto-resolves to `jetton-prepaid/pool.key` either way (override to point elsewhere). The pool key must exist first: `cd jetton-prepaid && acton script scripts/genkey.tolk` (or any deploy) generates + saves it.
```bash
# from the repo root (WorkingDirectory=/…/jetton-bomb):
TELEGRAM_BOT_TOKEN=... WALLET_SECRET=<hex ed25519 seed|key> \
  LS_CONFIG=./config.json \
  SHARDS_FILE=./tps_shards.json \
  ./go-spam/build/bot
```
Control wallet: `WALLET_SECRET` (hex, preferred) or `WALLET_MNEMONIC` (24 words) — both derive the same wallet (convert with `go run ./go-spam/cmd/derivekey <mnemonic-file>`). Backend is swappable at runtime: `/api <url> [key]` for toncenter, or `/config` to upload an LS config.

**Go standalone external spammer** (`cmd/spam`): same flags as `cmd/bot` env vars, plus positional `count freq`. See top-of-file comment in `cmd/spam/main.go` for the full flag/env table.

## Architecture

### TypeScript side

**Two contract languages** coexist: FunC (`.fc`/`.func`) and Tolk (`.tolk`). Both compile via `@ton/blueprint` to `build/<Name>.compiled.json`. Each contract has a compile config at `wrappers/<Name>.compile.ts`.

**Wrapper pattern**: Every contract has a TypeScript wrapper in `wrappers/<Name>.ts` that exports:
- A config type and `configToCell()` function for initial state
- A contract class with `createFromConfig()`, message senders (`sendDeploy`, `sendRun`, etc.), and getter methods
- The class implements `Contract` from `@ton/core`; methods take `ContractProvider` as first arg, which is auto-injected by `client.open()` / `provider.open()`

**Two ways to use wrappers**:
- Via blueprint's `NetworkProvider.open()` in scripts
- Via `TonClient.open()` directly (used in telegram bot, standalone scripts)
- Both return `OpenedContract<T>` with the same interface

**Key contracts**:
- `StaticTps` (Tolk) -- generates sustained TPS load on-chain via self-messaging loop. **Still active** — the Go bot's `/start` / `/shards` drive it (16 shard addresses).
- `WalletSpam` (FunC, `contracts/wallet_spam.fc`) -- **LEGACY** self-replicating pool wallet (reproduce opcode, optional extra currency). Superseded by the Tolk `WalletSpam` in `jetton-prepaid/` (see below); the Go bot no longer targets this FunC variant (`OldCodeHex` is gone).
- `JettonMinter`/`JettonWallet` (FunC) -- **LEGACY** jetton contracts. Superseded by the prepaid Tolk jetton in `jetton-prepaid/`.

**Shared FunC modules** in `contracts/`: `messages.func` (message builders), `op-codes.func`, `error-codes.func`, `jetton-utils.func`.

**Mnemonic management**: `scripts/lib/mnemonic.ts` reads/writes `mnemonic.txt` (gitignored via `*.txt`). Blueprint scripts use `WALLET_MNEMONIC` env var; spam scripts read from `mnemonic.txt` directly.

### Acton / Tolk side (`jetton-prepaid/`)

The **current** on-chain contracts, all Tolk, compiled by the `acton` CLI (`Acton.toml` lists them) to `build/<Name>.json` (base64 `code_boc64` + representation `hash`). Emulation-based tests, generated wrappers, and deploy scripts all live here.

**Contracts** (`jetton-prepaid/contracts/`):
- `JettonWallet` -- **plain** (non-sharded) **prepaid** jetton wallet. Every wallet is "born" with `PREPAID_BALANCE` (1,000,000) jettons, so any wallet can transfer with no prior mint — total supply is intentionally NOT conserved (load-test only). Address = pure state_init hash; data = `jettonBalance | owner | minter` (no code-ref, no split depth). `AskToTransfer` reads `internal_init_mode` from the first 2 bits of `customPayload` (nil→0): **0** = full recipient state_init (classic TEP-74, auto-deploys the recipient), **1** = bare / no state_init (for already-deployed recipients — cheaper). `WithdrawGrams` (op `0x6d8e5e3c`) sweeps all GRAM to a custom address + self-destructs (throwaway-wallet teardown).
- `JettonMinter` -- standard minter (admin, off-chain/on-chain metadata, mint/burn).
- `WalletSpam` -- self-replicating load-generator pool wallet, **ported from FunC `contracts/wallet_spam.fc` to Tolk**. Storage = `seqno | subwalletId | publicKey | minterAddress | ^jettonWalletCode` (the minter + jetton-wallet code ride in storage so each pool wallet can deploy its **own** prepaid jetton wallet in-chain — no more Go-side externals for jetton deploys). `Reproduce` (op `0xba5e5d50`) replicates the pool in chunks (`chunk` ≤ `MAX_CHUNK`=253, carried in the message; asserted on-chain) and optionally deploys each wallet's jetton wallet (`deployJetton` flag; `walletValue`/`jettonValue` are the single funding levers). `DestroyChain` tears the pool down as a **linear roll-up chain** (NOT chunked, no `DestroyLeaf`): every wallet destroys its OWN prepaid jetton wallet in-chain (forwarding a `WithdrawGrams` body built once off-chain and carried down the chain, funded with a fixed `jettonDestroyValue`) AND hands its whole balance to the very next wallet via `CARRY_ALL_BALANCE|DESTROY` (= its own self-destruct + funds the next hop), so all GRAM rolls down to the terminal wallet which sweeps it to `collector`. The whole teardown is ONE signed external on wallet 0 (like deploy) — no per-wallet externals. `spam_msg` and all Extra-Currency handling from the FunC original are gone. `onExternalMessage` keeps the **sig-first** layout `signature(512) ‖ subwalletId(32)|validUntil(32)|seqno(32)|(sendMode(8)|^msg)*`, so the Go external signer is unchanged.

**Shared modules**: `jetton-utils.tolk` (`calcDeployedJettonWallet` / `calcAddressOfJettonWallet`, `PREPAID_BALANCE`), `storage.tolk` (`WalletStorage`, `MinterStorage`), `messages.tolk` (jetton ops + `Reproduce`/`DestroyChain`/`TopUpGrams`), `sharding.tolk`, `errors.tolk`, `fees-management.tolk`. `WalletSpamStorage` is defined in `WalletSpam.tolk` itself.

**Deploy / tooling** (`jetton-prepaid/scripts/`): `deploy.tolk` (minter + full pool from one signed external, keypair = raw 32-byte ed25519 seed in `pool.key`, auto-generated + saved on first run; env levers above). `destroy.tolk` tears the whole pool down from one signed external (in-chain jetton destroy + linear roll-up to a collector). `scripts/utils/walletspam.tolk` holds the pool address helpers + kickoff-external builder. `scripts/_parity.tolk` prints the fixed-vector pool/jetton addresses the Go parity tests assert; `scripts/_transfer_cost.tolk` sums trace fees for transfer-cost measurement.

**Wrappers/tests**: `acton wrapper <Name>` generates `wrappers/<Name>.gen.tolk` (`fromStorage`/`deploy`/`sendX`/get-methods over the emulation network). Tests in `tests/*.test.tolk` run under the Tolk sandbox via `acton test`.

### Go side (`go-spam/`)

The Go side reimplements the load generator with native ed25519, goroutines, and a swappable backend. It does NOT compile contracts — it embeds the compiled code blobs from the **Acton/Tolk** side (`jetton-prepaid/build/`), as hex constants in `pkg/walletspam/code.go` (`CodeHex` = Tolk WalletSpam, `JettonWalletCodeHex` = Tolk JettonWallet). Regenerate these whenever those contracts change.

**Packages**:
- `pkg/backend` -- swappable RPC surface. `Backend` interface = `GetSeqno`, `GetBalance` (nanoTON account balance; uninit → 0; feeds the bot's `/check_balance` gate), `SendExternalMessage`, `SendExternalMessageWithInit` (external + dest state_init, for the native deploy kickoff), `RunGetMethod`, `Kind`, `Description`. Implementations: `LSBackend` (tonutils-go liteclient pool) and `HTTPBackend` (toncenter **v2** REST — `/sendBoc`, `/runGetMethod`, `/getAddressInformation`). The bot swaps live via `atomic.Pointer[Backend]`
- `pkg/pool` -- the 100k-`WalletSpam` shared pool with per-entry seqno cache (`Entry{mu, seqno, valid}`). `Pool` carries the `minter` + `jwCode` (both feed each WalletSpam's `dataCell`, so they fix the pool address). `Pool.Run` is a token-bucket driver. Entries are lazily created via `Get(id)`. `LoopConfig.Gate` is an optional pre-send predicate (runs before any seqno is acquired; returning false → `Stats.Skipped`, no seqno consumed, never Sent/Failed) — the balance gate (`/check_balance`, `cmd/spam --check-balance`) plugs in here
- `pkg/drain` -- shared `Tracker` behind the balance gate (used by BOTH `cmd/bot` `/check_balance` and `cmd/spam --check-balance`). A concurrent-safe map of drained sender ids: `IsDrained`/`Mark`/`RandomLive` (pick a live recipient) + `StopPercent`=75; the first crossing of 75%-drained fires `onStop` exactly once (the run auto-stops). "Drained" is monotonic (balance only falls during a run), so the map is a safe cache — a known-drained wallet is skipped with **no** RPC
- `pkg/walletspam` -- WalletSpam wrapper matching the Tolk contract. `dataCell` = `seqno | subwallet | pubkey | minter | ^jwCode`; address = `StateInit{Code, Data}.CalcAddress(0)` (canonical `0 0 1^code 1^data 0`). `New(subwallet, pub, priv, minter, jwCode, code)`. `BuildExternalBody`/`BuildExternalBodyWithMessage` produce the signed sig-first external cell (unchanged by the rewrite). No more `DefaultSpamMsg`/`OldCodeHex`/extra-currency
- `pkg/jetton` -- shared jetton-transfer external builder (`BuildTransferExternal` + `WalletAddress`/`TransferMessage`/`InitModePayload`). Used by BOTH `cmd/bot` `/jetton` and `cmd/spam --mode jetton`, so they emit byte-identical externals (golden test `pkg/jetton/transfer_test.go`). Imports only `pkg/walletspam` (pool imports walletspam, so this can't live in pool)
- `pkg/deploy` -- **native Go pool deploy (no acton).** `Deployer.KickoffBody()` builds the pool-key-signed external that (with wallet0's state_init attached) deploys wallet0 + fires the `Reproduce` chain — byte-identical to the acton `buildKickoffExternal` (parity `pkg/deploy/parity_test.go` vs `scripts/_deploy_parity.tolk`). No minter contract, no deployer wallet: fund wallet0, then send the kickoff. `Wallet0Funding()` = `(count+1)*(walletValue+feeSlack)`
- `pkg/walletv5` -- V5R1 control-wallet wrapper (used for static-TPS run/stop messages)
- `pkg/tpsmeter` -- **reusable network TPS + shard-count meter** (Go port of the Python `tpsmeter.py`). Source-agnostic engine (`Meter`) driven by a `Source` interface (`LatestMasterchainSeqno`/`Shards`/`BlockInfo`); it walks masterchain blocks + the basechain shard blocks they reference, counts transactions, and keeps an append-ordered history. Two `Source` impls: `ToncenterSource` (v2 HTTP: `getMasterchainInfo`/`shards`/`getBlockHeader`/`getBlockTransactions`, paginated, retries + 429 back-off) and `LSSource` (tonutils-go liteserver: resolves `(wc,shard,seqno)`→`BlockIDExt` via `LookupBlock`, caches per-poll tops so only catch-up intermediates re-lookup; `ProofCheckPolicyUnsafe` since only tx **count** matters). Both sources apply a shared **outbound RPS cap** (default 200, `0`=unlimited) on every request so the backfill can't overload the LS/toncenter. Query surface: `TPS(windowSec)` (total tx with `gen_utime` in the last window / window — **anchored at the latest INGESTED `gen_utime`, not wall clock**, so a meter that has fallen behind reports stale-but-real numbers rather than zeros: check `forward_synced` / a frozen `poll` counter before trusting a window), `ShardCount()`, `Snapshot()`. The **forward catch-up is batched** (`planForward`/`planForwardTargets`/`commitForwardBatch`): step `sq`'s predecessor tops are step `sq-1`'s own tops from `Shards(sq-1)`, a call that depends on no block being read, so a whole range's transition graph is computable up front and the walk costs **two parallel waves** (all `Shards`+`MasterchainIdentity`, then every block in one deduped `fetchStatsResults`) instead of a serial round-trip chain per masterchain block. Only the commits stay sequential — coverage and the store's contiguity check require it — and a step that fails to resolve or fetch truncates there, committing the prefix so the next poll resumes at the first missing block. This is what keeps a lagging meter able to regain the head: the serial walk ran at roughly the chain's own block rate (~1.4 mc/s vs testnet's 2.47), so once it fell behind it never recovered; `--workers` is the knob that sets the recovery rate. **`TPS(windowSec)` is the measurement primitive that doubles as the control-run metric**: after driving load for 15 min, `TPS(600)` = mean TPS over the last 10 min (the first 5 min of shard-split + ramp fall outside the window; the `Filling` flag / `*` marks a window whose history span is still shorter than the window). **`Options.Backfill`** (catch-up): on `Run`, a concurrent goroutine also walks masterchain seqnos BACKWARD from the start block — in descending parallel batches (`backfillBatch`=64; per-block latency, not RPS, is the walk's limiter), via `Shards(mc)` so it's correct across split/merge boundaries, fetching ranges strictly BELOW what forward has (no double-count) — until history spans the largest window (default 15 min). The stop target is **moving** (`currentNow - window`, not a fixed start-anchor): forward advances "now" while the walk runs, so backfill + forward meet in the middle and cover exactly the window — a fixed anchor would over-fetch old blocks that have already aged out of the live window by the time the walk reaches them. This fills the 1/5/15-min windows at once instead of ramping, and lets a control-run "look back" over load already running at start; progress is `Snapshot().BackfillActive`/`BackfillOldestUtime`/`BackfillTargetUtime` (shown as `[catchup Xs/Ys]`, Ys≈window). `NewLSSource(api, desc, rps)` takes an existing `ton.APIClientWrapped` so a future `cmd/spam` control-run can share the bot's LS pool; `NewLSSourceFromConfig(path, rps)` owns its own pool
- `cmd/bot` -- the Telegram bot. **One pool, sub-pool windows:** the legacy separate 100k pool is gone — the bot owns a single `pool.Pool` of `POOL_TOTAL` wallets (default 2,500,000; set it to what you actually deployed — a 5k mainnet pool is a first-class case) and every run drives a **window** of it. `/pool_size <n>` (`POOL_SIZE`, default 100000 = the legacy size, so the load profile is unchanged) cuts the pool into `floor(total/n)` **fixed, aligned** sub-pools and each run picks one at random. Fixed slices rather than a random offset: with a random start the middle of the pool is reachable by ~n windows and the ends by one, so the ends would be spent far more slowly; the `total%n` tail is deliberately never driven (a short slice would get a full slice's odds). `n` is CLAMPED to the deployed total, so a small pool just runs whole-pool — and setting `n` to the total is also how you deliberately drive everything (one sub-pool = the whole pool). Every pool-backed mode obeys the window, fat modes included; only `/hamster_kombat` ignores it and always drives the whole pool. The window is `pool.LoopConfig.WindowStart`/`WindowCount`; recipients and the `/check_balance` drain tracker are indexed relative to it, so "75% drained" means 75% of the wallets that run drives. Commands: `/help` (= `/start` with no arg: cheatsheet + status block), `/status` (the status block alone), `/pool_size`, `/start`, `/stop` (**stops EVERYTHING** — any pool mode + both static runs — and reports what it stopped; `/static_stop` is the old single-shard stop), `/static_stop`, `/fat_gram`, `/fat_jetton`, `/fat_size`, `/fat_count`, `/fat_mutate`, `/shards`, `/shards_stop`, `/jetton`, `/jetton_stop`, `/hamster_kombat`, `/hamster_kombat_stop`, `/gram`, `/gram_stop`, `/gassless_jetton`, `/gassless_gram` (+ `_stop`), `/external`, `/external_stop`, `/api`, `/config`, `/timeout`, `/errors`, `/initmode` (jetton transfer `internal_init_mode`: 0 = full state_init / classic, 1 = bare / no state_init since pool jetton wallets are pre-deployed; also `JETTON_INIT_MODE` env, default 0), `/retry` (on|off — toggle the pool refetch+resend on a failed send, live; `NO_RETRY` env, default on), `/check_balance` (on|off [threshold_nano] — gate jetton sends on the sender's on-chain GRAM balance to avoid burning gas on aborted transfers; `CHECK_BALANCE`/`MIN_SEND_BALANCE` env, default off / `jettonValue+0.01`. When on: a wallet below the threshold is Skipped (never Sent/Failed, no seqno consumed) and marked drained in a per-run `pkg/drain.Tracker` map — later picks of it skip with **no** RPC; the recipient is drawn from the live (non-drained) set; once **75%** of the pool is drained the `/jetton` run **auto-stops**. Fail-closed: a balance-RPC error also skips. Adds ~1 balance RPC per funded-wallet visit, so it's mainnet-oriented, RPS-tolerant.)
- `cmd/spam` -- standalone headless spammer (no TG), the primary devnet binary. Three modes via `--mode` (env `MODE`, `ONLY_EXT=1`→external): **jetton** (default — real `op::transfer` to a random pool wallet, same `pkg/jetton` builder as the bot's `/jetton`, byte-identical), **external** (empty signed externals, seqno bump only), and **targets** (each pool wallet pokes a big-state account). Jetton knobs `--value`/`JETTON_TRANSFER_VALUE`, `--init-mode`/`JETTON_INIT_MODE`. Requires a minter (`--minter` / `WALLET_MINTER`, part of every pool address; defaults to the same `SpamMinterTON` as the bot). **`--check-balance`/`--min-send-balance`** (env `CHECK_BALANCE`/`MIN_SEND_BALANCE`) run the same `pkg/drain` gate as the bot: skip sender wallets below the threshold (default 0.01 GRAM, or `jettonValue+0.01` in jetton mode), fail-closed on a balance-RPC error, auto-stop at 75% drained; `skipped` shows in the stats line.
  - **`--mode targets`** (`--targets <file>` / `TARGETS_FILE`) — each pool wallet sends one **bounceable** internal of `--target-nano` (env `TARGET_NANO`, default **1**) nanoTON with an **empty body** to an account from the file (raw `wc:hex`, one per line). The value nets ~0 (it bounces), but collating the poke forces the recipient's cells to load from CellDB — used to test whether touching the largest-**state** accounts slows/splits a shard (see `ton-index-go/cmd/bigstate`, which scans the toncenter kvrocks store for the biggest states; `cmd/pokes`/`cmd/pooladdrs` are the throwaway poke-history pullers). `--order random` (default) | `sequential` (env `TARGETS_ORDER`) — sequential walks the file in order via a shared atomic cursor (the `bigstate` output is size-sorted, so sequential = biggest-first, deterministic). **Every poke is logged to stdout AND `spam.log`** (`--spam-log`, append) with sender wallet / seqno / target / state size / ok|FAIL — so the exact target of each send is captured live (no reconstructing from toncenter); sizes auto-annotated from `<targets>.sizes` (`--target-sizes`). Stats + the final summary also tee to `spam.log`.
- `cmd/deploy` -- native pool deployer (devnet), three phases: `plan` (generates or reuses `pool.key`, prints eval-able `DEPLOY_WALLET0`/`DEPLOY_FUNDING_NANO`/`DEPLOY_MINTER`), `status` (detects a reusable complete pool, distinguishes an absent wallet0 with exit code 10, and resumes waiting for an incomplete deployment), and `broadcast` (sends the kickoff external, waits for wallet0 seqno→1 as a fast pre-check, then **waits for the TERMINAL wallet** — subwallet `count`, reached only after the whole reproduce chain unrolled — before `DEPLOY DONE`). The probe is `get_wallet_data` on a wallet's prepaid jetton wallet when `DEPLOY_JETTON=1`, else `seqno` on the WalletSpam; readiness = get-method returns nil error + non-empty stack; timeout → non-zero exit (aborts the caller). Each poll it probes ~20 sample subwallets spread across `[0,count]` and draws a **progress bar** (a `\r`-redrawn line: filled %, ~X/count wallets, samples, elapsed) so a multi-minute wait shows movement instead of looking hung; completion is **terminal-only** — the terminal (subwallet `count`) is the causally-LAST wallet in the reproduce chain, so its deployment means the ENTIRE pool is up (we require the full pool, so the spammer has no lingering failed% from an unbuilt tail — the samples are UX, the terminal is the real gate). If the terminal never deploys, the chain ran out of **fee cushion**: the rolling bank = `count × (WALLET_VALUE + FEE_SLACK)` and each wallet reserves `WALLET_VALUE`, so `FEE_SLACK` (default **0.1 GRAM**, raised from 0.01 which starved the tail on 10k pools) is the per-wallet fee headroom that rolls down — bump it if the tail stalls (devnet grams are free; excess just piles on the terminal wallet). Env mirrors the acton deploy (`WALLET_VALUE`/`JETTON_VALUE`/`FEE_SLACK`/`DEPLOY_CHUNK`/`DEPLOY_JETTON`/`WALLET_MINTER`) plus wait knobs `POOL_READY_TIMEOUT`/`POOL_POLL_INTERVAL` (flags `--pool-timeout`/`--poll-interval`). Sample-address computation lives in `pkg/deploy` (`ReadinessSamples`/`PoolWalletAddress`/`JettonWalletAddress`); the poll+bar loop (`waitReady`/`probeSamples`/`progressBar`) in `cmd/deploy`. See `docs/DEVNET_INTEGRATION.md` for the full `ton`-script wiring
- `cmd/tpsmeter` -- thin CLI over `pkg/tpsmeter`: prints one status line per tick (shard count + TPS 1m/5m/15m, `[catchup Xs/Ys]` while backfilling) with `>>> SPLIT a->b <<<` / `<<< MERGE >>>` markers on shard-count changes (block/per-shard tables from the Python dashboard dropped — only shards + TPS matter for the split test). Source select: `--ls-config`/`-l` (env `LS_CONFIG`) → LS, else HTTP `--api` (env `TONCENTER_ENDPOINT`, default `http://devnet-01.toncenter.com`) `--api-key` (env `TONCENTER_API_KEY`). Knobs `--catchup` (backfill to the largest window on start, **default on**), `--rps` (all-request cap, **default 200**), `--interval`/`--print`/`--windows`/`--workers`/`--history`. Devnet/testnet: `-l configs-private/tc-tgls-2pcs.json` (no key). Mainnet: `--api https://toncenter.com/api/v2 --api-key <key>`. With `--listen`+`--store` it runs as a **daemon** serving `/v1/health|status|series|summary` out of a bbolt history store instead of printing to stdout — that is what the session-stats dashboards proxy through `/api/tpsmeter/<endpoint>`
- `cmd/chbackfill` -- **one-off** historical loader for a tpsmeter store, straight from toncenter's ClickHouse. The meter's own catch-up walks the chain block by block over a liteserver, which caps history at what the LS still keeps (~5 days on testnet) and costs one RPC per block — a month is 13M+ blocks. This streams `<db>.blocks` in bulk instead: `mc_block_seqno` gives the shard-block → masterchain-block mapping, the `shards` column gives each masterchain block's shard-top set, and `root_hash`/`file_hash` give the checkpoint identity, so it rebuilds exactly the traversal invariants the live backfill builds. `--store hist.db --db mainnet_d --days 30 --ch <url> --user --password` (env `CH_URL`/`CH_USER`/`CH_PASSWORD`/`CH_DB`); afterwards run the meter on that same store and it takes over live from the head (its own `--catchup` completes immediately, coverage already spans more than the largest window). ~1 hour and ~1.7 GB per month per network. It commits through `Store.CommitBackfillBatch` — per-masterchain-block commits are fsync-bound at ~87 mc/s (20 h for a month), batched they run at ~60k mc/s

**TPS / shard-split load-testing plan** (see the [[shard-split-loadtest-plan]] memory for the full "why"): the manual test is a **binary search for the shard-split TPS threshold** (200↔400 TPS, 10-TPS precision; per step: wait for the network to merge back to 1 shard, hold the target TPS ~10 min, split = success). The Go side automates the two measurement halves: (1) `cmd/tpsmeter` replaces the Grafana glance (live shard count + windowed TPS); (2) `pkg/tpsmeter`'s engine is built so `cmd/spam` can grow a **deterministic control-run** subcommand — drive load for 15 min, then print `TPS(600)` (mean over the last 10 min) — to minimise the manual factor and give a reproducible per-run TPS number on devnet (no ClickHouse / no toncenter v3 there — that's why the engine is `Source`-modular and LS-capable). On mainnet/testnet the same shard/TPS reads are also available straight from ClickHouse (`transactions.now` for TPS, `blocks` `uniqExact(shard)` for split count) — see [[toncenter-mainnet-infra-access]]

**Fat modes** (`/fat_gram`, `/fat_jetton`, `/fat_size`, `/fat_count`, `/fat_mutate` in the bot — senders come from the run's `/pool_size` sub-pool window like every other mode, so driving the whole pool against the 431k-fat recipient set means setting `/pool_size` to the deployed total; `cmd/spam --mode jetton-fats`): pool wallets send to the **FatReproduce big-state accounts** that inflate the controlled testnet (tiers 10/25/50/100/200 KB, 781k accounts, ~160 GB). The point is the collator, not the transfer — touching an account forces a walk of its storage dict (`prelim_storage_stat`, the long_collation axis), so `/fat_size` picks how much walking each message costs. **`/fat_count <n>`** narrows how MANY fats a run spreads over (default: the whole tier; `/fat_size` resets it, since a count only means something against a tier): the tier is cut into fixed aligned slices of `n` and each run draws one, exactly like `/pool_size` does to the senders, so repeated runs wear the tier evenly instead of re-touching one hot subset. The chosen slice is log-only — the bot's status just reports the count (`targets: 1000 fat accounts of 200 KB`), since the range of derived addresses tells the operator nothing. Recipient addresses are **DERIVED, never stored** (`pkg/fatpool`): a FatReproduce address is a pure state_init hash over `(code, subwalletId, publicKey)` — no minter, no size — so a 19-entry manifest of (pool pubkey, count, size) reproduces all 781k, replacing a 37 MB dump. `pkg/fatpool/derive_test.go` verifies every derived address against `jetton-prepaid/fats-160/*.addrs` (gitignored; the test skips without it). `/fat_jetton` forces **init mode 0** (the fat's jetton wallet is a stranger's and NOT pre-deployed) and needs **`FAT_FORWARD_TON` > 0** (default 0.01) — the transfer_notification is what actually lands on the fat; with 0 only its jetton wallet is touched. A fat transfer attaches its OWN `FAT_JETTON_VALUE` (default **0.05**, asserted to sit at least 0.02 GRAM above `FAT_FORWARD_TON`) rather than `/jetton`'s `JETTON_TRANSFER_VALUE`: the forward is paid out of the attached value and nothing comes back, so a level tuned for the refunding pool-to-pool hop (e.g. 0.01) makes every fat transfer abort. It sets `response_destination` to **addr_none** so no `op::excesses` comes back — which keeps it at the same **four transactions** a pool-to-pool transfer takes, the fourth being the notification instead of the excesses. The tradeoff is drain: `/jetton` gets its leftover back inside the pool (~0.012 net), while a fat transfer leaves the whole attached value behind — `FAT_FORWARD_TON` on the fat itself, the remainder on the fat's jetton wallet; `FAT_MUTATE` (default **off** = read-only touch, live via **`/fat_mutate on|off`**) toggles touch-and-mutate vs read-only touch — the A/B for separating "the collator WALKED the big state" from "it also REBUILT it"; it is read per send so it applies mid-run, unlike `/fat_size` whose recipient list is captured at start. Note the bot's `*_stop` commands are hidden from the Telegram command menu (handlers and `/help` still list them).

**Gasless modes are always highload-batched** (`/gassless_jetton`, `/gassless_gram`, CLI `highload-*` and `gassless-*` aliases): the shared `highload.Batcher` routes by the target's **top two address bits** to **four Highload-V3 relayers by default**; `HIGHLOAD_SHARDS=16` (`--highload-shards 16` in CLI) routes by the first nibble to the original 16-wallet set for the testnet dispatch-queue experiment. The default four retain that set's nibble 0/4/8/c addresses, derived from the pool key + `HIGHLOAD_TTL`. Every external, even a one-item batch, sends `internal_transfer` to its own highload, whose action list emits the funded target-signed `sint` requests. Windows are **500ms**, without phase offsets; an address limiter shared across bot runs caps **all attempts including retries at 2 externals/s**. Batches are bounded by **254 actions / 60 KiB full external BoC**; overflow waits for the next window. The self-message carries 0.01 GRAM for compute, which credits the same highload. Retries reuse the exact external/query_id (`/retry` / `--no-retry` apply at batch level). `Pool.Run` uses `BatchedSend` with `RemotePendingFor=130s`: a target's seqno cannot be reused before observed on-chain; an uncertain post-dispatch error retains that reservation. `Sent`/`Failed` count logical submissions, while `BatchSend`/`BatchRetry` count real external RPC attempts and `Batches` counts accepted externals. Jetton attach default is **0.01**, relay **0.012** (CLI `GASSLESS_JETTON_VALUE`, explicit `--value` wins); native GRAM funding is below. The bot watches the configured relayer balances every 30s and warns below `HIGHLOAD_MIN_BALANCE` (default 1000), never deploying or topping them up. Real testnet batch checks on 2026-10-01: one GRAM item = 4 tx, mixed GRAM + jetton = 8 tx, no aborts. See README's mandatory gasless batching section for traces.

**Gasless GRAM funding:** `/gassless_gram` and CLI `highload-gram` / `gassless-gram` default to `GRAM_TRANSFER_VALUE + 0.001` (0.002 at the default 0.001 transfer), via `gram.DefaultRelayValue`. Real testnet verification on 2026-10-01 covered accrued storage rent and a maximum 123-byte comment without spending the sender's old balance. `GASSLESS_GRAM_RELAY_VALUE` (alias `GASLESS_GRAM_RELAY_VALUE`) overrides the general relay env for GRAM; explicit CLI `--relay-value` wins over either env. General relay env overrides still apply when no GRAM-specific env is set. Jetton default remains 0.012.

**Jetton transfer** (`pkg/jetton`, called from `cmd/bot/jetton.go` and `cmd/spam --mode jetton`): the WalletSpam signs an external carrying one `op::transfer` (`0xf8a7ea5`) to its **own pre-deployed** jetton wallet → `op::internal_transfer` to the recipient → `op::excesses`. The **recipient is a RANDOM OTHER POOL WALLET** (`pool.Get(rand).Wallet.Address()`, chosen by the caller), not a fresh stranger address: pool jetton wallets are all pre-deployed by `Reproduce`, so a transfer neither re-deploys nor sheds the ~0.0002 GRAM storage reserve into an uncontrolled address — the GRAM stays inside the pool, dropping per-transfer drain toward the fee floor. Because recipients are pre-deployed, `/initmode 1` (bare) is the cheapest correct mode. `jetton.WalletAddress` is a pure state_init hash (`coins|owner|minter`, `CalcAddress(0)` — no split depth, no code-ref, no shard-prefix surgery). **No StateInit is ever attached** to `op::transfer` (pool jetton wallets are pre-deployed in-chain by `Reproduce`). `jetton.InitModePayload` encodes `internal_init_mode` in `customPayload` (`/initmode` in the bot, `--init-mode`/`JETTON_INIT_MODE` in `cmd/spam`): 0 → no customPayload (full recipient state_init), 1 → 2-bit cell (bare). Cross-toolchain address parity (Go ↔ Tolk) is asserted by `pkg/walletspam/parity_test.go` and `cmd/bot/parity_test.go` against a fixed vector from `jetton-prepaid/scripts/_parity.tolk`; the full signed external is locked by `pkg/jetton/transfer_test.go`

**`Pool.Run` loop semantics**:
- Uses **shuffle-once iteration** (`rand.Perm` + cursor) so every wallet in `[0, count)` is hit exactly once per epoch, then reshuffles. Avoids birthday-paradox collisions vs uniform random selection. Same-wallet revisit interval ≈ `count / freq` seconds — must be > 2× block time to avoid hash-order collisions inside a block
- One goroutine per send. Throttled at `MaxInflight` (default `2*freq + 10`)
- `SendTimeout` is a `func() time.Duration` so `/timeout` takes effect mid-flight

**Direct `runOne` send pipeline + retry** (batched gasless retry/reservation rules are above):
1. `acquireSeqno` (1st): cache hit → use; cache miss → `cfg.FetchSeqno`
2. `cfg.Send` (1st). On success: `Sent++`, done
3. On first send error: invalidate cache, `Retried++`, then `acquireSeqno` (2nd, always fetches), then `cfg.Send` (2nd). On success: `Sent++`. On failure: `Failed++` and surface both errors
The retry exists because at high freq the LS does TVM-simulation against a possibly-stale view, and re-fetching from the same LS aligns us with its current view for the second attempt. **Opt out** (single-attempt, the pre-`22f35a4` behavior of commit `d09c5d4`) via `LoopConfig.NoRetry` (a live `func() bool`): the bot's `/retry off` + `NO_RETRY` env, or `cmd/spam --no-retry` / `NO_RETRY`. In that mode step 3 just invalidates the cache + `Failed++` (no refetch/resend; `Retried` stays 0).

**`Stats` counters** (in `pkg/pool/pool.go`):
- `Sent` / `Failed` -- final outcome (after any retry)
- `Throttled` -- skipped due to `MaxInflight` cap
- `Skipped` -- dropped by the pre-send `LoopConfig.Gate` hook BEFORE any seqno/send (so it never touches Sent/Failed and can't desync the cache); the bot's `/check_balance` uses it for drained wallets. 0 when no Gate is set
- `Retried` -- events that entered the retry path
- `Send0` / `Seqno1` / `Send1` / `Seqno2` / `Send2` -- direct-send backend-RPC breakdown. Gasless item submissions do not increment the send counters; their actual external attempts increment `BatchSend` / `BatchRetry`. Total backend RPS = sum of all seven counters. `Batches` counts accepted batch externals.
- `Inflight` -- live goroutine count

**Bot status messages** use Telegram's `sendRichMessage` HTTP endpoint directly (the `go-telegram/bot` v1.20 lib doesn't wrap it yet — see `cmd/bot/rich.go`'s `sendRichHTML`). Layout: `<h1>` send-rate, `<h2>` fail-rate + window-accepted %, `<pre>` monospace stats block (totals/retried/failed/throttled/skipped/inflight), a `drained X/N (%)` line when `/check_balance` is on, then two collapsible `<details>` spoilers — API RPS breakdown table and the errors histogram. Plain-text fallback via `stripHTML` if the rich endpoint isn't accepted.

**Error aggregation** (`cmd/bot/errstack.go`): per-error strings get normalized via regex (IP:port → `[NODE]`, 64-hex hash → `[TX]`, block coords → `([W],[SHARD],[SEQ])`) plus boilerplate stripping. Bucketed by type. `/errors on|off` toggles the breakdown appendix; rolling snapshots also go to `errors.log` (so we don't accumulate per-error torrents).

**Pool key management** (Go): `pkg/backend/mnemonic.go` `LoadKeypairFromSeedFile` reads the raw 32-byte ed25519 seed from `POOL_KEY_FILE` (default `../jetton-prepaid/pool.key`, the same file the Acton deploy writes) for the spam pool keypair — `ed25519.NewKeyFromSeed` == acton `crypto.seedToKeyPair`, so Go and Acton derive the identical pool addresses. Devnet `ton start`/`start-bulk` remove this key before resetting the chain; the first spam run generates a new key, while later spam runs on the same chain reuse it and the deployed pool. The control wallet (V5R1) still takes its 24-word mnemonic from `WALLET_MNEMONIC`.

## Testing

**TypeScript** tests use `@ton/sandbox` to simulate the blockchain locally (`tests/<Name>.spec.ts`, `jest`). The sandbox provides `Blockchain`, `SandboxContract`, and treasury wallets.

**Acton/Tolk** (`jetton-prepaid/`, the current contracts) tests run in the Tolk emulation sandbox via `acton test` (`tests/*.test.tolk`): `expect(...)`, `testing.treasury`/`isDeployed`/`getAccountBalance`, `net.send`/`net.sendExternal`. These are authoritative for `JettonWallet`/`JettonMinter`/`WalletSpam` behavior (reproduce chain, chunked destroy, external sig/seqno guards, `internal_init_mode`, transfer cost).

**Go**: unit tests live next to the packages (`go test ./...`). Notably the **cross-toolchain parity** tests assert Go output matches the Tolk contracts for fixed vectors — **regenerate the golden constants whenever `WalletSpam`/`JettonWallet` storage or code (or the `Reproduce`/kickoff layout) changes**, since that shifts every address + the deploy external:
- address parity: `pkg/walletspam/parity_test.go`, `cmd/bot/parity_test.go` ← `acton script scripts/_parity.tolk`
- native-deploy kickoff parity: `pkg/deploy/parity_test.go` ← `acton script scripts/_deploy_parity.tolk` (hashes printed as decimal uint256; the Go test compares `big.Int` decimal)
- jetton-transfer external golden: `pkg/jetton/transfer_test.go` (self-locked; update knowingly)
- bench W5 / prepaid-JW / fat address parity (the `--mode fats` path): `pkg/walletv5/parity_test.go`, `pkg/fats/parity_test.go` ← `bench-state-gen derive --seed-hex <seed> --index <i>` (see `ton/benchmark/state-gen.cpp`)
