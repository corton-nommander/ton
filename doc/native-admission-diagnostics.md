# Native admission diagnostics

`total.ext_msg_batch_diagnostics` is a cumulative ExtMessagePool statistics key.
The same fields appear as `name=value` in the existing, rate-limited native
batch admission log. Statistics use `name:value`. The instrumentation does
not change admission policy, status codes, status messages, or wire ordering.

## Result counts

`not_ready_total` counts failed final physical input statuses with code 651.
Each input slot contributes once after duplicate input statuses resolve. One
NTRN parent counts once regardless of its logical output count; two duplicate
input slots count twice; a later retry is a new physical attempt. Successful
statuses and errors with other codes do not contribute. Cause counters sum to
`not_ready_total`:

| Field suffix after `not_ready_` | Meaning |
| --- | --- |
| `snapshot_changed` | The pinned masterchain snapshot changed before a signed run could be reserved. |
| `account_changed_verification` | The source account revision changed before verified-message reservation. |
| `account_changed_insertion` | The source account revision changed before mempool insertion. |
| `account_changed_commit` | The source account revision changed before mempool commit. |
| `canonical_watermark_lag` | Loaded account state predates the observed canonical watermark. |
| `masterchain_unavailable` | Missing or invalid masterchain state, or missing pinned configuration. |
| `shard_unavailable` | A required source/destination shard cannot be located in the pinned/applied configuration. |
| `mempool_full` | Global external-message mempool capacity rejected the parent. |
| `per_address_limit` | The external-message per-address mempool limit rejected the parent. |
| `other` | An unclassified code-651 diagnostic, including propagated manager errors. |

Classification uses existing exact diagnostics, with bounded prefixes for the
two capacity errors. Changed or unknown diagnostics remain counted in `other`.
The entry branch lacking masterchain state uses explicit context because its
legacy message is simply `not ready`; that message from another origin is
not automatically classified as missing masterchain state.

Counts cover every body reaching the pool batch coroutine, including generic
external messages and batches generated by the individual-native-submit server
coalescer. Use a pure NTRN workload to interpret them as signed-run parent
counts. Existing `total.ext_msg_batch_admission` accepted/rejected counters are
the corresponding completed-status denominator. Its message count includes
started batches and may include unfinished work.

A completed pool result does not establish that the liteserver RPC delivered
it: an outer query may already have timed out. Query rejections before the pool,
upstream coalescer overflow, and query-cache duplicate rejection are excluded.
The generator can classify capacity diagnostics separately from `not_ready`;
therefore pool code-651 totals need not equal its retry-reason count. Existing
`shard_manager_wait_notready` counts failed manager awaits, while this key
counts their final input statuses, which can fan out to several parents.

## Batch and wall-time scopes

`active_batches` counts started pool coroutines without a recorded completion
or abandonment. `peak_active_batches` is its process-lifetime high-water mark.
`finished_batches` counts complete pool results, including rejected results.
`aborted_batches` counts task-frame cleanup without a complete pool result;
partial status vectors are not added to result counters. Aborted bookkeeping
posts back to the pool actor and can briefly lag frame cleanup. Caller timeout
alone does not imply a pool abort: detached work may still finish.

Each timing prefix has `_samples`, `_sum_s`, and `_max_s` fields:

| Prefix | One sample covers |
| --- | --- |
| `residence` | Pool coroutine entry through completed result accounting. |
| `aborted_residence` | Pool coroutine entry through abandoned-frame cleanup, measured before posting bookkeeping. |
| `shard_wait` | One completed native shard-manager await, including timeout/error results. |
| `verification` | Native prechecks, signature-task dispatch and the group wait, only when at least one signature task was dispatched. |
| `snapshot_age` | Initial native snapshot pin through the post-verification snapshot check, once per batch reaching that check. |
| `changed_snapshot_age` | The same age, once per batch that actually rejects at least one signed run for snapshot change. |

Durations are monotonic wall time, not CPU time. Residence excludes upstream
coalescer and actor-mailbox waiting before coroutine entry. Stages overlap;
their times must not be summed as independent execution costs. A completed
stage retains its sample if a later stage aborts. An abandoned await contributes
no completed-stage sample. Nonfinite or negative durations are ignored.

For a measurement interval, subtract starting from ending cumulative counts
and sums, then compute `delta(sum_s) / delta(samples)` when the latter is
positive. Lifetime maxima and `peak_active_batches` cannot be subtracted to
recover interval maxima. Sample `active_batches` during the interval when
comparing concurrent admission pressure under strict validator reuse.

## Verification scope

`test-native-admission-batch` includes regressions for cause classification,
code/acceptance filtering, mixed final input statuses and duplicate slots,
explicit missing-masterchain context, overlapping completed/aborted batches,
and invalid timing samples. These helper tests do not simulate a complete
liteserver timeout or force a live masterchain/account-revision race. Runtime
before/after counter deltas are still required to establish which causes explain
an observed retry increase.
